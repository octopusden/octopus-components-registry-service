## Why

Archiving a component is the last, recording step of retiring it. The substantive steps happen by hand in the external systems: the remaining issues are closed, the issue-tracker project is reclassified and renamed, the TeamCity projects are archived, the repositories are archived. CRS records the outcome by setting `ComponentEntity.archived`.

CRS records it unconditionally. Nothing asks whether the preceding steps happened, so a component can be marked retired while its repositories are live, its builds still run, and issues are still open against it. None of those external archives is reversible.

There is a second problem that only shows up once the checks exist. **Infrastructure is shared between components.** `TeamcityProjectEntity` documents its `project_id` as unique — *"one row per TC project, referenced by any number of `VersionLineEntity` rows"* — and `VersionLineEntity` adds that the referenced project is *"shared (deduplicated by project id)"*. `addTeamcityProjects` does a find-or-create with no uniqueness guard, so the ordinary v4 write path produces the shared case, and an existing integration test deliberately links one project to two components. A target still used by a live component must not be archived — so "this target is not archived" is the correct end state for the component being retired, not a failure. A gate that demanded otherwise would make such a component permanently unarchivable.

## What Changes

CRS gains an archive-readiness check: a read-only answer describing, per target, whether the retirement steps were carried out. Nothing about how `archived` is written changes — callers ask for the answer before archiving and apply it themselves.

- **A readiness endpoint.** `GET rest/api/4/components/{idOrName}/archive-readiness` returns one entry per target — the component's open issues, the issue-tracker project, each TeamCity project, each repository — carrying that target's outcome, the reason, and the live components that still use it. Plus a single `ready` verdict, which is what callers gate on.
- **One entry, one rule.** The component's open issues and its issue-tracker project are separate entries even though both are read from the same project, because they obey opposite rules: open issues are scoped to this component's own version prefix, so no other component's use of the project can excuse them; the project is shared, so a live component still using it means "not retired" is the correct end state. Combined into one entry, the outcome would be a mix of two verdicts and a caller could not tell which one produced it. Split, every entry's outcome comes from exactly one rule and `sharedWith` is empty wherever sharing cannot excuse.
- **Three outcomes, not four.** `COMPLETED`, `NOT_COMPLETED`, `UNKNOWN`. A target shared with a live component reports `COMPLETED` with a non-empty `sharedWith`; there is no separate skipped outcome. Sharing does not block, so the gate does not need a fourth state for it — but the sharing is reported as structured data because two consumers need it: the Portal, to tell the operator that a target was deliberately left running, and the follow-up work that performs the archives, to name every target it will skip.
- **`UNKNOWN` is distinct from `NOT_COMPLETED` and blocks.** `Repository.archived` in octopus-vcs-facade is nullable and documented as *"treat null as unknown, not as 'not archived'"*. An unreachable system is not evidence that a target is unarchived, so it gets its own outcome and its own reason, and readiness fails closed.
- **A permanently unreadable target must not deadlock a component.** Because `UNKNOWN` blocks and there is no override, a target whose state can never be read would make its component unarchivable forever. Three real cases do that — the repository was deleted rather than archived, the build project no longer exists, and the integration credential expired with nobody fixing it — and retrying helps in none of them. Three rules resolve it: a system positively reporting a target **absent** passes, since a deleted repository is not live infrastructure and absence is a stronger end state than archived; each system is **proved live once per call** before any absence is trusted, because a hardened host answers "not found" for targets a credential may not see, and without the proof a silently expired credential would make every component look ready; and a system that is **not configured** contributes no entries at all, which is what makes turning off a permanently broken integration a real remedy rather than a way to block everything forever.
- **No change to any write path.** `deleteComponent` — CRS's soft delete, which is what the Portal's Archive button calls — keeps its exact current behaviour, as do `updateComponent`, `createComponent` and the bulk import. The check sits in front of archiving, not inside it.
- **The retired issue-tracker categories are configuration.** An issue-tracker project has no archived flag; retirement is recorded by reclassifying the project. Which categories mean "retired" is the issue tracker's own data and can be renamed there without a CRS release, so CRS reads the set from configuration rather than compiling it in. With nothing configured the project-archived part is `UNKNOWN` — never a silent pass.
- **A shared-usage helper, computed once.** The follow-up work that performs the archives asks the identical question. Computed twice, the two will eventually disagree — and the disagreement means the check says "safe" while the executor says "shared", or the reverse. One helper, one answer.

## Affected areas

- `components-registry-service-server` only. No schema change, no migration: every input already exists — `ComponentEntity.archived`, `VcsSettingsEntryEntity.vcsPath`, `VersionLineEntity` → `TeamcityProjectEntity.projectId`, and the effective `(jiraProjectKey, jiraVersionPrefix)` pairs `ComponentConfigurationEntity` resolves per component (base row plus version-range overrides — see design.md's Context and decision 15; a component can carry more than one such pair at once, and the check reuses the registry's own existing resolution, `computeEffectiveJiraPairs`, rather than reading one row's columns).
- **New client dependencies.** CRS has no issue-tracker client at all today — every build file was checked. The Atlassian REST Java client (`-api`, `-core`, plus `io.atlassian.fugue:fugue`) is taken for issue search, which is the check's core question and which the octopus client has no form of — its `JiraClient` exposes `createIssue`, `updateIssue`, `getAssignable`, `getProject`, `getActiveSprint`, `moveIssuesToSprint` and `addRemoteLink`, and nothing else. The octopus `jira-client` is taken for the project category: its `Project` DTO carries `key` and `projectCategory`, and the category is how a retired project is recorded. Both are needed, and neither is used for anything beyond those two reads. The octopus client is published under the `octopus-external-systems-clients.version` already pinned for `teamcity-client`, so it adds a module, not a version.
- **The vcs-facade version is confirmed, not just named.** `org.octopusden.octopus.vcsfacade:client:3.0.36` is required for `getRepository(sshUrl)` and the nullable `Repository.archived`. Neither exists at 3.0.27, the newest version resolvable from the local caches at the time this was written: that `VcsFacadeClient` has no `getRepository`, and its `Repository` — which lives in the sibling `vcsfacade:common` artifact, pulled in transitively, not in `client` — carries only `sshUrl`, `link` and `avatar`. `3.0.36` was downloaded from Maven Central and inspected directly: it is the published `latest`/`release` version, `VcsFacadeClient.getRepository(String)` exists and calls `GET rest/api/2/repository?sshUrl={sshUrl}`, and `Repository.getArchived()` returns a boxed (nullable) `Boolean`. The shape this change needs is real and already released.
- **The TeamCity read needs a new query, not a wider `fields` list.** The sync's existing call is scoped by `parameter:(name:COMPONENT_NAME)`, so it cannot see descendants of a component's project that do not carry that parameter — and archiving a TeamCity project archives its whole subtree. The gate issues its own call using the `affectedProject` locator, which teamcity-client `2.0.98` already supports.
- **No existing endpoint or service method changes behaviour.** This is additive: new clients, a new query, a new service, a new endpoint. `deleteComponent`, `updateComponent`, `createComponent` and `ImportServiceImpl` are untouched.
- No API response shape changes. The readiness response is a new endpoint, not an addition to `ComponentDetailResponse` — it makes live calls to three external systems and must never sit on the component detail path.
- **The committed OpenAPI spec must be refreshed in the same change.** `OpenApiV4SpecTest` is untagged, so it runs under `test` → `check` and fails the build on any drift between the live v4 controllers and `src/main/resources/openapi/v4.json`. Adding an endpoint without running `./gradlew :components-registry-service-server:generateOpenApiDocs` breaks the [1.0] gate. The refreshed file is also what the Portal vendors to generate its types.

## Out of scope

- **Performing the archives.** This change only reports; it does not archive a repository, a TeamCity project or the issue-tracker project, and needs no write permission in any of them. The archives are follow-up work, and that work is where the service account gains project-admin rights in three systems — which is why it needs its own security review and is not smuggled in here.
- **Server-side enforcement.** CRS does not refuse a write because readiness fails. The answer is advisory, and the caller decides. Two consequences follow and are accepted: a caller that skips the check can still archive an unready component, and there is a window between a caller's check and its archive request in which the external systems can change. Enforcing at write time would close both, but it would also mean modifying `deleteComponent` — and since that is CRS's soft delete, it would make deleting a mistakenly created component require its retirement steps to be complete first. That trade was declined; the existing archive path is left exactly as it is.
- **Un-archiving.** No check. Nothing in the external systems is restored either.
- **Separating the two meanings of `archived`.** The flag serves both "retired per the retirement steps" and "soft-deleted". That collision is real and will confuse someone later, but untangling it is a data-model change well beyond this gate.
- **The permission names.** Archiving is governed by `DELETE_COMPONENTS` and restoring by `ARCHIVE_COMPONENTS`, which reads backwards. Used as they are.

## Rollout note

Safe to deploy on its own: nothing that works today changes, and a caller that never asks for readiness behaves exactly as before. The endpoint simply becomes available.

The check depends on three external systems being reachable, and reports `UNKNOWN` for any it cannot consult. `UNKNOWN` makes `ready` false, so during an outage the answer is "cannot confirm" rather than "not ready" — and the reason names the system, so a caller can say so instead of showing a timeout or, worse, telling someone to go archive a target whose state was never read.

Because the answer is advisory, an outage does not stop archiving at the CRS level. What it stops is any caller that respects the verdict.

If an integration is broken beyond repair, the remedy is to unconfigure it: an unconfigured system contributes no entries, so archiving works again. That is deliberately the only escape — there is no per-component override — and whether it is enough on its own is left open rather than settled here.

## A note on the retirement steps

This proposal refers to the steps that must precede archiving. That process is documented outside both repositories, so nothing here links to it and a reader cannot verify the list from the codebase. The spec therefore defines the checks CRS actually performs, rather than restating the process as though the process itself were the requirement.

That distinction matters most for the issue tracker, where the gap is widest. Retiring a project there is five steps: rename it to `X <name> [ARCHIVE]`, set its category to `X Archive`, then switch its issue-type, workflow, permission and notification schemes. **CRS checks one of the five** — the category.

The other four are not oversights:

- The four scheme changes are administrative settings, readable only with issue-tracker administrator rights. This check holds no elevated permission anywhere by design, and asking for admin read in a third system for an advisory check is not a trade worth making. The archiving follow-up is where elevated rights are argued for, under its own security review.
- The rename is observable but not matched. A project name is free text, so a matcher guesses at spacing, bracketing and capitalisation, and a false `NOT_COMPLETED` on a correctly retired project sends someone to redo finished work — which is how a gate stops being trusted. The category is chosen from a fixed list, so exact matching is sound.

So `COMPLETED` on the issue-tracker project entry means the marker is set, not that the procedure was completed, and the spec says exactly that. Presenting it as more would be the failure this change exists to prevent, in a new place.
