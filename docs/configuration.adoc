== Overview
Components Registry is a registry of all link:{glossary-component-link}[components] developed in the organization.
It keeps basic parameters of components required for organizing automated release management and Escrow package generation.

WARNING: All components must be registered in link:{components-registry-link}[Components Registry]!

Components Registry stores the following information about Components:

* Release Management parameters (used for automated link:{release-management-automation-link}[registration of releases and generation of client release notes])
** Desired JIRA Project Key
** Major version format in JIRA
** Release version format in JIRA
** VCS repository url
** VCS repository branch
** VCS repository release tag format
* Build/Escrow parameters (used for link:{escrow-automation-tool-link}[Escrow package generation])
** build system (Maven, Gradle etc)
** groupId/artifactId of artifacts produced and published in Artifactory at each release (*it's recommended to use unique groupId for the component*)
** required build tools and their versions (Java, Maven, Gradle)
* Distribution parameters
** whether the component has its own distribution
** whether it is delivered to an external customer
** artifact coordinates to be published

== Where configuration lives
Configuration is stored in a database and is edited through the Web UI or the REST API.

There is no configuration file to edit, no branch to create and no pull request to merge. Every
change takes effect immediately, is attributed to its author and is recorded in an audit log.

NOTE: Configuration used to be kept as ConfigSlurper (Groovy) files in a Git repository, changed by
raising a pull request. That is no longer the case. A read-only Groovy-style rendering of a
component is still available (see <<Viewing a component as code>>) for anyone used to that shape,
but it is a projection - it is not parsed back and cannot be edited.

== How to register or change a Component
=== Through the Web UI
The Web UI is the normal way to register and change components. It offers the same fields described
in <<Component configuration reference>>, validates them as you type, and shows the resulting
version ranges.

=== Through the REST API
The REST API is the same surface the UI uses, and is the way to script bulk or repeatable changes.

The endpoints below are the ones needed for day-to-day configuration, not the whole surface. The
service publishes its own OpenAPI specification and serves an interactive Swagger UI alongside it,
which is the authoritative and always-current reference - request and response schemas, every
endpoint, and the ability to try a call. The same specification is committed in this repository
under `components-registry-service-server/src/main/resources/openapi/`.

Components are addressed by *id*, a UUID - not by component name. Resolve the name first:

----
GET /rest/api/4/components?search=<component name>
----

Read a component, including all of its configuration rows:

----
GET /rest/api/4/components/{id}
----

Create a component:

----
POST /rest/api/4/components
----

Change a component:

----
PATCH /rest/api/4/components/{id}
----

A `PATCH` body carries only the fields being changed. Two optional fields are worth setting on every
call, because both are recorded on the audit row:

* *jiraTaskKey* - the JIRA issue motivating the change, e.g. `ABC-123`
* *changeComment* - free text describing why

Example - move a component to a newer Java version:

----
PATCH /rest/api/4/components/{id}
{
  "baseConfiguration": { "build": { "javaVersion": "17" } },
  "jiraTaskKey": "ABC-123",
  "changeComment": "component's own build moved to JDK 17"
}
----

Allowed values for the enumerated fields are served by the registry itself, so they never go stale
in this document:

[cols="2,3"]
|===
|`GET /rest/api/4/components/meta/java-versions` |Java versions accepted by *javaVersion*
|`GET /rest/api/4/components/meta/maven-versions` |Maven versions accepted by *mavenVersion*
|`GET /rest/api/4/components/meta/build-systems` |values accepted by *buildSystem*
|`GET /rest/api/4/components/meta/escrow-generations` |values accepted by escrow *generation*
|`GET /rest/api/4/components/meta/systems` |values accepted by *system*
|`GET /rest/api/4/config/field-config` |which fields are editable, and their labels
|===

=== Through crsctl
`crsctl` is a read-only command-line client for the same API, useful for scripting queries and for
inspecting a component from a terminal. It cannot change configuration.

== Viewing a component as code
----
GET /rest/api/4/components/{id}/as-code
----

Returns a human-readable, Groovy-style rendering of the component definition - the reverse of the
legacy import. It is read-only: the rendering is a projection and is never parsed back.

== Component configuration reference
Each component has one *base configuration* covering all versions, and optionally *field overrides*
that apply to a version range (see <<Version ranges>>).

=== Component-level fields

* *componentDisplayName* - display name of the component, e.g. in DMS
* *parentComponent* - grouping components in DMS
* *clientCode* - if the component is client specific
* *solution* - `true` for a solution
* *componentOwner* - username of the component's owner, without the domain part
* *releaseManager* - comma-separated usernames of the component's release managers
* *securityChampion* - comma-separated usernames of the component's security champions
* *system* - used for differentiation between different corporate policies (license control, etc)

Person fields are validated against the employee directory when the component is created or
changed.

=== Build fields

* *buildSystem* - MAVEN, GRADLE etc
* *javaVersion*, *mavenVersion*, *gradleVersion* - build tool versions
* *buildFilePath* - path to the build file, when it is not at the repository root
* *buildTasks* - build tasks to execute
* *systemProperties* - system properties passed to the build
* *projectVersion* - required Cards version for building the escrow of this component

=== Artifact fields

* *groupId* - comma-separated list of groupIds of artifacts that belong to the component. It's
  recommended to use a unique groupId
* *artifactId* - artifactId regex pattern of artifacts that belong to the component

=== VCS fields

* *vcsUrl* - repository url
* *branch* - repository branch. If not specified, `master` is used
* *tag* - tag used for releases labelling

=== JIRA fields
Parameters related to build/release registration in JIRA and generation of client release notes:

* *projectKey* - JIRA project key
* *majorVersionFormat* - format of major version in JIRA (refer to <<Version format>>)
* *releaseVersionFormat* - format of release version in JIRA
* *versionPrefix*, *versionFormat* - see <<Version format>>

=== Version ranges
Different configurations of a component depending on the version of its release are supported. This
is expressed as a *field override*: a single field, scoped to a version range.

----
GET    /rest/api/4/components/{id}/field-overrides
POST   /rest/api/4/components/{id}/field-overrides
PATCH  /rest/api/4/components/{id}/field-overrides/{overrideId}
DELETE /rest/api/4/components/{id}/field-overrides/{overrideId}
----

An override names the attribute it replaces, the range it applies to, and the value:

----
POST /rest/api/4/components/{id}/field-overrides
{
  "overriddenAttribute": "build.javaVersion",
  "versionRange": "[1.1.517,)",
  "value": "21"
}
----

Version range has Maven 2.x/3.x format.

Examples of version range:

[cols="1,1"]
|===
|(,1.0]
|version \<= 1.0

|[1.0]
|version = 1.0

|(,1.0],[1.2,)
|version \<= 1.0 or version >= 1.2

|(,1.1),(1.1,)
|version <> 1.1
|===

WARNING: Version ranges of a component should have no intersections! Overlaps are rejected when the
override is saved.

Which versions of a component are in scope at all is a separate setting:

----
GET /rest/api/4/components/{id}/supported-versions
PUT /rest/api/4/components/{id}/supported-versions
----

=== Version format
Base version formats like *majorVersionFormat* and *releaseVersionFormat* are configured using following variables:

* *$major* - first item of the build version
* *$major02* - first item of the build version in format %02d
* *$minor* - second item of the build version
* *$minor02* - second item of the build version in format %02d
* *$service* - third item of the build version
* *$service02* - third item of the build version in format %02d
* *$fix* - forth item of the build version
* *$fix02* - forth item of the build version in format %02d
* *$fix04* - forth item of the build version in format %04d
* *$build* - fifth item of the build version
* *$build02* - fifth item of the build version in format %02d
* *$build04* - fifth item of the build version in format %04d

Jira version format defined by *versionFormat* is extended version of base format that is configured using following variables:

* *$versionPrefix* - version prefix
* *$baseVersionFormat* - base version format

Usually it has value *$versionPrefix-$baseVersionFormat*

=== Dynamic variables resolution

Following parameters support dynamic variables resolution:

* *vcsUrl*
* *branch*
* *tag*
* *buildFilePath*
* *systemProperties*

Available variables are:

* all base version format variables (refer to Version format, extended version format variables like *$baseVersionFormat* are not supported)
* *$module* - component name
* *$version* - component build version
* *$cvsCompatibleVersion* - the same as *$version* but all dots are replaced with hyphen-minus symbols
* *$cvsCompatibleUnderscoreVersion* - the same as *$version* but all dots are replaced with underscores

Example:
----
$module-$major02.$minor02.$service02
----

=== Multiple release branches
If your component uses multiple release branches, specify them in the `branch` parameter, separated by the `|` symbol.

Example:
----
master|release/$major.$minor
----

=== Escrow section
The escrow section of the component configuration describes parameters related to Escrow package generation.

Below is the list of available parameters:

* *generation* - Escrow generation mode. Can be one of:
  ** *AUTO* - Escrow automation is supported. Escrow Test configuration supported.
  ** *MANUAL* - Escrow Test configuration to be created.
  ** *UNSUPPORTED* - Escrow Test configuration should not be created.
* *buildTask* - Custom build task to execute during escrow package generation (optional). For example: `"clean build -x test"`.
* *providedDependencies* - Comma-separated list of provided dependencies that should be included in the escrow package (optional). Format: `"groupId:artifactId:version"`.
* *diskSpaceRequirement* - Disk space requirement for escrow package generation (optional). Can be specified as:
  ** Number in bytes (e.g., `1073741824`)
  ** String with units: `"1GB"`, `"512MB"`, `"1024KB"` (or `"1G"`, `"512M"`, `"1024K"`)
* *additionalSources* - Comma-separated list of additional source paths to include in the escrow package (optional). For example: `"spa/.gradle,spa/node_modules"`.
* *reusable* - Whether the escrow package can be reused by other components that depend on this component (default: `true`). When set to `true`, the escrow process will reuse already built escrow package instead of rebuilding dependencies.

=== Distribution section
The distribution section of the component configuration describes how the component is distributed.

Below is the list of available parameters:

* *explicit* - indicates whether component has its own distribution (true/false)
* *external* - indicates whether component is delivered to external customer or used only internally (true/false)
* *GAV* - comma-separated list of MAVEN artifact coordinates
* *DEB* - comma-separated list of DEBIAN artifact coordinates
* *RPM* - comma-separated list of RPM artifact coordinates
* *docker* - comma-separated list of Docker image coordinates where image tag implicitly starts with a component version and optionally ends with a specified suffix (e.g. `:arm64` after evaluation with version  `:1.2.3` will become `:1.2.3-arm64`)

*GAV*, *DEB*, and *RPM* parameters can be configured using Expression Language.

WARNING: At least one of *GAV*, *DEB*, *RPM*, *docker* parameters should be defined for *external* *explicit* component!

==== Expression Language
The rules of how to calculate distribution coordinates can be configured using Expression Language.

Available variables are:

* *${component}* - component name
* *${version}* - component build version
* *${major}* - first item of the build version
* *${minor}* - second item of the build version
* *${service}* - third item of the build version
* *${fix}* - forth item of the build version
* *${build}* - fifth item of the build version
* *${env.<NAME>}* - <NAME> environment variable
* *${baseDir}* - user.dir system property

==== MAVEN artifacts configuration
Each artifact can be either:

* loaded from MAVEN storage (then one should specify MAVEN GAV *except version*)
* taken from local FS on build agent and uploaded to MAVEN storage (then one should specify file URL)

File URL can be extended with query parameters *artifactId* and/or *classifier* (that affects calculation of MAVEN GAV to be used for uploading).

Example:
----
org.company.newcomponent:artifact:jar,file:///target/application-${version}.exe?artifactId=NewComponent
----

== Audit
Every change is recorded. The history of a component, and the recent history across the registry,
are available through:

----
GET /rest/api/4/audit/{entityType}/{entityId}
GET /rest/api/4/audit/recent
----

This is what replaced the Git history of the old configuration files.
